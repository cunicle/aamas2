\section{Parallel Deciders, Protocols, and Role Cues}
\label{sec:setup}

\subsection{The Agent and Its Action Interface}
\label{sec:interface}

A tool-calling agent receives a request $q$ and a set of tool schemas, and acts by issuing a set of calls $A=\{a_1,\dots,a_n\}$, each naming a tool and binding its arguments. When $n>1$, the turn is a joint action. We score it as a set, as BFCL does~\cite{patil2025bfcl}: the turn is correct if its calls match the reference calls one to one, in any order.

The dLLM agent writes $A$ as a JSON array onto a canvas of mask tokens (Figure~\ref{fig:setup}a). To make every action well formed, its interface writes the syntax of the turn in advance as a \emph{skeleton} (the number of calls, the tool and argument names, all brackets and quotes) and masks only the argument values, each in a \emph{slot} of $\ell$ mask tokens, its \emph{slot length}. The slots that hold the same argument in different calls of the same tool form a \emph{sibling group}. Our skeleton is an oracle, built from the reference calls, so that every remaining error is an error in a value; Section~\ref{sec:discussion} discusses what the oracle hides.

Two details of the interface matter below. First, the skeleton writes the closing delimiter of each value after its slot (the closing quote of a string, or the comma or brace after any other value). A value ends early when the model writes its own closing token inside the slot; the rest of the slot is then set to padding, and both are dropped from the output. Second, as in grammar-constrained decoding, each slot accepts only tokens of its argument's JSON type, its closing tokens, and padding: string slots exclude tokens with a quote or backslash, integer slots accept only digits, a sign, and a leading space, and float slots also a point and an exponent. Section~\ref{sec:length} varies both. The AR agent uses the same skeleton and type mask, writing each value until its closing token or the slot length.

\subsection{Deciders and Protocols}
\label{sec:protocol}

At each denoising step, the dLLM predicts every masked position from the current canvas and commits some of them, never revising a committed token; tokens committed in the same step are chosen given the canvas \emph{before} that step, so they cannot see each other. We call each slot a \emph{decider}, since its first committed token usually decides which entity it names. The deciders are positions of one network: they share one policy and differ only in their position on the canvas and in what has been committed when they move. In the terms of team decision problems~\cite{radner1962team,marschak1972teams}, a parallel turn has one payoff (the turn is correct or not) and an information structure that the decoding schedule sets. Unlike in team theory, the policy is fixed by training and never optimized for this payoff; we use the terms only for who moves together and who sees what, and the predictions below are hypotheses, not consequences of the model.

To compare, we give the same requests to \emph{teams of $n$ LLM agents}, one per call. Each agent is a separate generation of the same model (\qwen, or \dream decoding one token per step in confidence order), sees the skeleton of its own call only, and receives the request followed by a note on the protocol (Figure~\ref{fig:setup}b; the supplementary material gives all texts). A \emph{protocol} says which deciders move together and what each sees:
\begin{itemize}
\item \emph{One canvas.} With $k$ tokens per step in confidence order, the $k$ most confident masked positions move together; with $k=1$, \emph{one token per step}, every decider sees every earlier commitment. Left-to-right decoding (LTR) fixes the order of moves. A confidence threshold $\tau=0.9$~\cite{wu2026fastdllm} commits every position whose top probability exceeds $\tau$, and the most confident position alone when none does.
\item \emph{Teams.} Agents act at the same time, seeing no other call, or in turns, seeing the calls made so far. They are anonymous, numbered, or numbered and told the rule (``By convention, assistant $i$ makes the $i$-th of the calls, in the order in which the request mentions them''). \emph{Position agents} get no note but the skeleton of the whole turn, and fill call $i$ only; the other calls' values stay masked (\dream) or are placeholders (\qwen), so an agent sees where its call stands but none of the other agents' choices.
\end{itemize}

\subsection{Role Cues and Hypotheses}
\label{sec:predictions}

The sibling deciders of a turn must each take a distinct entity, the one its own call needs. A shared policy can set them apart only through something they share that orders the candidates, or something that differs between them:
\begin{enumerate}
\item \emph{Mention order.} The request names its entities in some order. Taking the $i$-th mentioned entity for the $i$-th call is a convention any decider that knows its index can follow; on set-scored requests every assignment is correct, and the mention order is the one a shared policy is most likely to reproduce.
\item \emph{Role.} A role is a slot's position on the shared skeleton, or an agent's number in its prompt. A role sets deciders apart only if the policy's output depends on it, and helps only if something orders the candidates: ``you are the second call'' does not say which of all US cities is the second.
\item \emph{Slot length.} In training every mask hides exactly one token, so the mask count always equals the length of what it hides. An interface that sets slot lengths supplies this cue whether or not it is correct.
\end{enumerate}

\noindent We test three hypotheses about these cues (Sections~\ref{sec:ordered}--\ref{sec:length}).
\begin{itemize}
\item[\pred{1}] \emph{Order coordinates.} When the request orders its entities, slots that decide in the same step take the $i$-th entity for the $i$-th call, so committing many tokens per step costs little.
\item[\pred{2}] \emph{Symmetric deciders collide.} When nothing orders the candidates, deciders that move at the same time take the same value, and deciders that take turns do not.
\item[\pred{3}] \emph{Length is a cue.} A slot's length steers its value: a slot longer than its value gets a longer value, and a slot with a sibling's length gets that sibling's value, at any $k$, including one token per step.
\end{itemize}
If a prompted number acts as a role, simultaneous numbered agents take the $i$-th entity of an ordered request or list without colliding.

\subsection{Models, Data, and Measures}
\label{sec:models}

\paragraph{Models.} \dream~\cite{ye2025dream} (Dream-v0-Instruct-7B) is a dLLM with full bidirectional attention, initialized from \qwen-7B. \llada~\cite{bie2025llada2} (LLaDA2.0-mini, a mixture of experts with 16B parameters, 1.4B of them active per token) is a dLLM that denoises 32-token blocks left to right; only 3.1\% and 2.3\% of the sibling slot pairs in the two BFCL categories share a block, so its calls take turns and it serves as a control. The AR reference is \qwen-7B-Instruct~\cite{qwen2024qwen25}, the instruction-tuned version of the model that \dream is initialized from. All models see the same system prompt, which lists the tools as JSON and asks for a JSON array of calls, and decode greedily, except where we sample at temperature $T=0.7$ (Section~\ref{sec:symmetric}).

\paragraph{Data.} We use the \texttt{parallel} and \texttt{parallel\_multiple} categories of BFCL v4~\cite{patil2025bfcl}: 400 requests with 2 to 8 calls (2.9 on average) and 3,063 value slots. Subsets: the \emph{equal-length} requests (213 for \dream's tokenizer, 216 for \llada's), in which each argument has slots of one length in every call that uses it; the 104 \emph{team-symmetric} requests, in which the sibling calls of each tool share one skeleton and slot lengths, so that only an agent's prompt sets it apart from the agents that call the same tool (86 of them use one tool); the 165 \emph{swap} requests, which have sibling slots of different lengths; and \llada's subset of 100 requests (34 of the swap requests) for its runs with wrong lengths. For requests in which nothing orders the calls, we add 105 \emph{choose-N} requests (Section~\ref{sec:symmetric}).

\paragraph{Slot lengths.} \emph{Exact}: each slot has as many masks as its own reference value has tokens, tokenized on its own. \emph{Surplus} $+s$: every slot gets $s\in\{1,2,4,8\}$ extra masks. \emph{Swap}: slot lengths are rotated by one position within each sibling group. \emph{One slot longer}: in each sibling group with unequal lengths, the first slot shorter than the longest gets the longest sibling's length, and all others stay exact. These derive from the reference values: they are diagnostic interventions, not lengths an agent could set. \emph{Estimate}: lengths that the model predicts in one forward pass (Section~\ref{sec:design}).

\paragraph{Measures.} \emph{Set accuracy} is the share of requests that the BFCL checker accepts. The \emph{cross-call error rate} (\ccer) is the share of requests with at least one cross-call error, found by an optimal one-to-one matching of predicted and reference calls: a duplicated or missing call, a value that belongs to another call (bound), a string that puts a piece of another call's value in place of a piece of its own (chimera), or an argument that the reference shares across calls but the prediction does not. At the slot level we read each slot's value from its own tokens and classify it as its own reference value, a sibling's value (\emph{fit} if it has exactly the slot's length), an \emph{overfill} (its own value followed by more), or anything else. \emph{Order} measures whether the $i$-th call takes the $i$-th mentioned entity, with the reference order as a proxy for the mention order (they differ in 9 of the 104 team-symmetric requests). For paired comparisons on the same requests we give the difference with a 95\% bootstrap interval over requests and the $p$-value of an exact McNemar test, and say where a result does not survive Holm's correction over all our 48 paired tests; for single rates, a Wilson interval.
